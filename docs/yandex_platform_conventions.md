# PharmaCheck AI — соглашения для платформы Yandex Cloud

Версия: 1.1
Применение: весь production-код и инфраструктура проекта

## 1. Общий принцип

Проект реализуется под нативные интерфейсы Yandex Cloud. Названия моделей, полей запросов, способов авторизации и форматов событий нельзя переносить из OpenAI API по аналогии без проверки официальной документации Yandex Cloud.

Если Yandex AI Studio предоставляет OpenAI-совместимый интерфейс, его использование должно быть отдельным осознанным решением. Для структурированного аналитического ответа PharmaCheck выбран Yandex AI Studio Responses API; его поля проверяются по документации Yandex, а не переносятся по аналогии с другим провайдером.

## 2. Yandex Cloud Functions

- Runtime: `python312`.
- Версия Python: 3.12.
- Точка входа: `index.handler`.
- Файл `index.py` располагается в корне пакета функции.
- Сигнатура синхронного обработчика: `def handler(event, context):`.
- Асинхронный обработчик допустим, если используемые библиотеки и тесты подтверждают корректную работу в `python312`.
- HTTP-ответ функции — словарь с `statusCode`, `headers` и строковым `body`.
- Время до завершения вызова проверяется через `context.get_remaining_time_in_millis()` перед дорогими внешними операциями и повторными запросами.
- `context.request_id` используется как технический идентификатор вызова в логах.
- Клиенты HTTP и другие безопасные переиспользуемые объекты создаются на уровне модуля, чтобы повторные вызовы тёплого экземпляра не выполняли лишнюю инициализацию.
- Нельзя хранить пользовательское состояние в глобальных переменных: оно может исчезнуть при холодном старте или сохраниться между вызовами одного экземпляра.

## 3. Yandex API Gateway и Telegram webhook

- Спецификация шлюза: OpenAPI 3.0.
- Интеграция: `x-yc-apigateway-integration` с `type: cloud_functions`.
- Версия события фиксируется явно: `payload_format_version: "1.0"`. На значение по умолчанию `0.1` не полагаемся.
- Cloud Function остаётся приватной. API Gateway вызывает её от сервисного аккаунта через `service_account_id` с минимальной ролью `functions.functionInvoker` на конкретную функцию.
- Вход Telegram принимается только методом `POST` на выделенном пути, например `/telegram/webhook`.
- Обработчик учитывает, что `event["body"]` приходит строкой, а `event["isBase64Encoded"]` может потребовать декодирования.
- Перед разбором проверяются наличие тела, допустимый размер и корректность JSON.
- Повторные Telegram updates обрабатываются идемпотентно по `update_id`; повтор не должен запускать вторую медицинскую проверку или отправлять дублирующий ответ.
- При регистрации webhook задаётся `secret_token`; до выполнения внешних запросов обработчик сверяет заголовок `X-Telegram-Bot-Api-Secret-Token` со значением `TELEGRAM_WEBHOOK_SECRET` безопасным сравнением.
- Функция всегда возвращает корректный HTTP-ответ. Ошибка медицинского источника или модели не должна превращаться в утечку traceback пользователю.

## 4. Сервисные аккаунты и IAM

- Cloud Function выполняется от отдельного сервисного аккаунта PharmaCheck AI.
- API Gateway использует отдельный либо строго ограниченный сервисный аккаунт для вызова приватной функции.
- Применяется принцип минимальных прав; роль `editor` не используется как постоянное production-решение.
- Для обращения к Yandex AI Studio предпочтительно использовать IAM-токен сервисного аккаунта, доступный в `context.token.access_token`, если выбранный API поддерживает этот способ.
- Долгоживущий статический ключ не создаётся, если задачу можно решить IAM-токеном среды выполнения.
- Необходимые роли AI Studio назначаются на нужный каталог или более узкий поддерживаемый ресурс; точное имя роли проверяется перед развёртыванием по актуальной документации выбранного API.

## 5. Секреты

- Токен Telegram и ключи внешних медицинских источников хранятся в Yandex Lockbox.
- Секреты не записываются в репозиторий, системный промпт, `evidence_package`, ответы модели и обычные логи.
- Сервисному аккаунту функции выдаётся `lockbox.payloadViewer` только на необходимые секреты.
- Способ передачи Lockbox-секрета в Cloud Function повторно проверяется при развёртывании, поскольку готовая serverless-интеграция может иметь статус Preview.
- Имена переменных конфигурации пишутся в верхнем регистре, например `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET`, `YC_FOLDER_ID`, `YANDEXGPT_MODEL_URI`.

## 5.1. Лицензии медицинских данных

- DDInter разрешён только для конфигурации `noncommercial_mvp`.
- Коммерческая конфигурация обязана передать `commercial_use=True`; адаптер DDInter в этом режиме прекращает запуск до чтения данных.
- Snapshot DDInter не включается в репозиторий, образ коммерческой версии или резервную копию, предназначенную для передачи покупателю.
- Переход к монетизации требует отдельной лицензии DDInter либо замены провайдера через общий интерфейс `InteractionSource`.

## 6. YandexGPT и Yandex AI Studio

- YandexGPT вызывается только после формирования полного `evidence_package`.
- Перед вызовом модели Python формирует `deterministic_assessment` с допустимыми уровнями результата; ответ модели за пределами `allowed_levels` отклоняется.
- Невалидная или неполная матрица `пары действующих веществ × обязательные источники` прекращает обработку до платного вызова модели.
- Модель не получает инструменты для самостоятельного медицинского поиска в MVP.
- Конкретный URI модели хранится в конфигурации, а не в системном промпте.
- Контрольные тесты закрепили YandexGPT Pro 5.1 с явным URI `gpt://<folder_id>/yandexgpt-5.1`; алиасы `latest` и `rc` для production не используются.
- Выбран интерфейс Yandex AI Studio Responses API: `POST https://ai.api.cloud.yandex.net/v1/responses`.
- В запросе Responses API используются проверенные поля `model`, `instructions`, `input`, `max_output_tokens` и `text.format` с типом `json_schema`.
- При аутентификации IAM-токен передаётся как `Authorization: Bearer <token>`; идентификатор каталога передаётся в `x-folder-id`, когда это требуется интерфейсом.
- Для вызова модели сервисному аккаунту достаточно роли `ai.languageModels.user` на каталоге.
- Ответ дополнительно проверяется Pydantic/JSON Schema в Python независимо от заявленного формата API.
- Параметры OpenAI, включая `reasoning_effort`, `reasoning.effort`, `text.verbosity` и `safety_identifier`, не передаются YandexGPT.
- Имена параметров не смешиваются между интерфейсами: для выбранного Responses API используется `max_output_tokens` и `text.format`, а не поля другого SDK или Completion API.
- Для воспроизводимости медицинского анализа используется низкая вариативность генерации; конкретное значение температуры выбирается по тестам, а не предполагается заранее.
- Любое изменение модели, версии, промпта, схемы или параметров запуска требует повторного прохождения контрольных сценариев.

## 7. Тайм-ауты и ошибки

- Для каждого внешнего источника и YandexGPT задаются отдельные тайм-ауты короче общего тайм-аута Cloud Function.
- Полный URL openFDA не журналируется, поскольку при использовании ключ передаётся в query-параметре `api_key`.
- Перед повтором проверяется оставшееся время через контекст функции.
- Повтор допускается только для временной сетевой ошибки или невалидного формата модели и ограничивается заранее заданным числом попыток.
- Ошибка обязательного медицинского источника приводит к ⚪, а не к 🟢.
- Повторная ошибка YandexGPT приводит к безопасному техническому ответу без оценки совместимости.
- HTTP-коды и внутренние коды ошибок проекта разделяются. Пользователю не показываются внутренние идентификаторы ресурсов, токены, traceback или полный ответ внешнего API.

## 8. Логи и данные

- Структурированные логи содержат `context.request_id`, Telegram `update_id`, внутренний `request_id`, этап обработки, длительность и безопасный код результата.
- В обычные логи не записываются полный текст медицинских документов, системный промпт, токены, прямые идентификаторы пользователя и необработанный ответ модели.
- Для диагностики сохраняются идентификаторы источников, версии документов, версия модели и результат валидации без чувствительного содержимого.
- Политика хранения логов и пользовательских данных задаётся до production-развёртывания.

## 9. Зависимости и структура пакета функции

- Зависимости Python фиксируются с совместимыми версиями и устанавливаются из файла, поддерживаемого Cloud Functions.
- Импортируемые модули и `index.py` находятся в структуре, корректной для корня ZIP-пакета функции.
- Размер пакета, длительность холодного старта и общий тайм-аут проверяются на реальной Cloud Function, а не только локально.
- Локальные тесты используют сохранённые примеры события API Gateway выбранной версии `1.0` и Telegram Update.

## 10. Правило проверки документации

Перед написанием кода для конкретного сервиса проверяются актуальные официальные страницы Yandex Cloud по:

1. runtime и формату handler;
2. версии payload API Gateway;
3. методу и формату Yandex AI Studio;
4. URI и версии выбранной модели;
5. IAM-ролям;
6. квотам, тайм-аутам и лимитам;
7. способу передачи Lockbox-секретов.

Предположение, сделанное по опыту с другим облаком или API, не считается подтверждением.
